# 文档索引与维护职责

本索引定义各类文档的唯一职责与读取方式。先按根 [AGENTS.md](../AGENTS.md) 确定任务模式；相关记忆的检索仍遵循其 §0.1。

## 按任务读取

| 当前任务 | 先确定什么／读哪里 | 何时追加资料 |
|---|---|---|
| 问答／状态查询 | 定位所问对象的业务来源或计划、状态条目 | 结论依赖当前实现或旧证据已失效时，回查对应文件与实际结果 |
| 分析／规划 | 从任务目标确定比较依据，读相关需求或规范 | 有未决依赖、冲突或可行性问题时，再读对应实现与专题资料 |
| 实施／修复 | 读命中的 [指南](guide/README.md)、业务来源与已有实现 | 本次改动跨越数据、播放、页面等边界时，补相应指南与验收入口 |
| AI/Agent 规范维护 | 读根规范、本文、目标技能／指南，判断归属与重复 | 规则涉及实际能力才核对代码；有明确对标目的时读取参考项目的对应规则 |

每次追加阅读要能回答一个当前未决问题。上下文已有且仍有效的内容不重复加载；能确定任务边界、判断依据、相关实现或规则归属及完成条件后，进入工作，不为了文档齐全通读整个目录。资料缺失时先搜索现有引用与替代来源，确认影响范围后按根规范决定继续或询问。

## 1. 文档分层

| 层级 | 回答的问题 | 权威入口 | 更新时机 |
|---|---|---|---|
| 根规范 | 有哪些工程边界、必须读什么、如何交付 | [AGENTS.md](../AGENTS.md) | 已授权的规范变更；任务相关事实纠错按根维护边界处理 |
| 开发指南 | 用已有代码怎样实现、哪些错误必须拦住 | [guide/](guide/README.md) | 已授权的规范变更；任务相关事实纠错按根维护边界处理 |
| 项目技能 | 某类任务如何选择分支、执行和结束 | [.agents/skills/](../.agents/skills/) | 已授权的流程变更；任务相关事实纠错按根维护边界处理 |
| 产品/业务 | 应有的交互、算法、计数和内容口径 | 下表业务文档 | 已确认规则变更时 |
| 实施状态 | 现在实现到哪里、哪些冲突未裁决 | [product_status.md](product_status.md) | 涉及能力或差异变化时 |
| 规划与评审 | 要做什么、依据与实施顺序 | [优化规划](engineering_optimization_plan.md) | 方案或进度变化时 |
| 记忆 | 下一次任务如何找到有效结论和踩坑 | [.memory/](../.memory/SUMMARY.md) | 按根规范 §0.1 判断增量 |

工程规范不承载未经确认的产品决定；状态文档不把源码现状反向定义为产品规则。历史文档保留价值时标注范围，不让新旧口径并列生效。

规则、事实、建议分别书写，强度按根规范解读。指南保留稳定方法和接口契约；临时问题及关闭证据归实施状态；特定时点的评审依据归报告。其他位置保留必要提示和链接，避免复制完整问题描述。

## 4. 修改时的同步关系

- 课程策略变化：算法业务文档 → engine/policy → 适用测试；若触及持久化，同时核对 Schema、迁移和状态映射。
- 页面行为变化：专项需求 → 实现 → 实施状态；不能只更新开发指南或 Daily。
- Token 变化：设计系统 → AppTheme → 受影响页面视觉验收；三者不允许长期分叉。
- 内容变化：Schema/词表 → 实际资源 → 模型路径和资源声明 → 完整性及语义验收。
- 平台/依赖变化：锁文件与工程 → 环境说明 → 发布验证；不凭构建脚本存在就写“发布通过”。

## 5. 文档状态与可信度

新建或实质修改方案、评审、需求和状态文档时，在开头简述用途、适用范围与当前状态；涉及决定写确认依据，涉及现状写核对日期和来源，被替代时指向新来源。普通错字或链接修正不触发全篇重新确认，也不要求批量给历史文档补模板。

| 状态 | 可以据此判断什么 | 使用边界 |
|---|---|---|
| 草案／建议 | 备选方案与理由 | 不构成产品决定或执行授权 |
| 已确认要求 | 适用范围内应该怎样 | 附用户指令或已确认业务来源；仍需分别确认实施与验证状态 |
| 已实现／已验证 | 指定版本、范围或环境内的事实 | 写实际证据；局部验证不扩大为全流程通过 |
| 待核对／历史／已替代 | 检索线索与旧背景 | 返回当前来源，不直接作为新任务要求 |

一份文档可包含不同状态的条目，应在条目处区分。缺少确认依据时明确标注待核对；Agent 写出的标题、总结、建议或 Daily 不会自行完成确认。用户授权只覆盖其确认的对象和范围，不能借整份报告扩大解释。

## 6. 提示词与技能的维护

技能承载可复用任务流程，不重复复制根规范或业务公式。修改时按实际复杂度写清：适用／不适用场景、输入及查找来源、工作模式、按需资料、执行分支、缺信息或失败时的处理、产物与完成条件。简单任务不必机械增加同名章节。

description 用具体任务意图描述触发条件；正文复用现有授权和任务范围。参考项目的提示词先提取有效方法，再按本项目适配；工具、文件和平台能力需核对，不能把参考项目的事实当作本项目能力。

## 7. 文档验收

规范与技能变更先检查归属、相互冲突、规则强度和已确认范围，再用代表任务走读：输入是否能找到、分支是否可选、阻塞是否局部、产物是否回答原问题。对边界变化尤其检查“仅分析”“已授权实施”“事实纠错”和“证据不足”的处理；这是提示词的静态检查，不代表已验证未来 Agent 的执行效果。

在根目录运行 `python3 tool/check_docs.py` 和 `git diff --check`。前者检查部分本地引用与记忆格式／预算，不是完整 Markdown 或协议语义校验；章节锚点、引用式链接、日期有效性等已知边界见 [复评](reviews/engineering-review-2026-10-18.md)。仍需人工核对本次受影响的引用、规则与状态；工具通过不替代这些判断。
